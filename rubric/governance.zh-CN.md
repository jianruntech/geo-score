# 量表治理

*English: [governance.md](governance.md)*

> 2026-10-16 起执行。这一页讲 AIV 量表怎么改、谁能提、同一个版本怎么做到谁跑都是同一个分，以及量表和标准组织的关系。
> 这一页本身的改法和量表一样：公开改，记进更新日志。

## 谁在维护，我们卖什么

量表、工具和榜单由见润科技维护。我们同时卖 GEO 服务：给网站做诊断，帮客户把站改到分数更高。这是利益冲突，下面的规矩就是因为它才定的。

- 量表、工具和榜单都免费。我们不卖认证、不卖标识、不卖「达标」标签，也不卖榜单上的位置。徽章和反向链接不会让分数动一分（[README](../README.zh-CN.md)）。
- 网站上不上榜单，看的是行业和语言的覆盖、知名度，从来不看它是不是谁的客户或竞争对手。
- 我们给客户做项目，用的是公开发布的版本，不改一处。客户的基线和拿来对比的复测，用同一个量表版本、同一个工具版本，所以客户的分数涨了，不可能是因为量表改了。
- 我们自己提的改动，和别人走同一套公开流程，并写明是我们提的。

## 谁能提改动

谁都能提。不需要是客户、贡献者，也不需要是公司。开一个[口径提案](../.github/ISSUE_TEMPLATE/rubric_proposal.yml)，表单要你写：

- **改什么**：写到别人照着就能实现的程度；
- **证据**：你看到了什么，在多少个站上，多长时间，哪几家引擎。公开研究和你自己的实地数据都可以，写明是哪一种；
- **别人怎么从站外核实**：要靠引擎内部数据或私有统计才能查的项，进不了一个谁都能跑的量表。

没有任何观察的提案会被关掉。样本小但写得清楚，就够开始讨论。
如果改动的结果和你有商业利益，比如你卖的产品会因此占便宜，在提案里写明。这不会让提案作废，只是让读的人能掂量。

跑量表时发现的口径歧义，比如两个实现给同一页打出不同的分，开 issue 打 `rubric` 标签，记进 [open-questions.zh-CN.md](open-questions.zh-CN.md)。

## 怎么改

版本号规则照[量表 README](README.md#what-bumps-the-version)：

| 改动 | 版本 | 流程 |
|---|---|---|
| 错别字、措辞更清楚、换个更好的例子 | 不变 | 普通 pull request |
| 加减检查项、改权重、改一项过不过的判定 | 小版本（v1.1 到 v1.2） | 下面五步，公开征求意见至少 30 天 |
| 改支柱结构 | 大版本（v1 到 v2） | 下面五步，公开征求意见至少 60 天 |

一条提案进不进新版本，由维护者决定，理由写在 issue 里；不采纳的，关掉时写明原因。

1. **提案。** 一个打了 `rubric` 标签的 issue，讨论都在那里公开进行。
2. **草案。** 维护者认为提案成熟了，就开一个 pull request，放进下一版的文件：中英两版量表、JSON、中英两版证据表、一份标定记录（草案给公开榜单打出来是什么样、哪些站会动），以及一份用它打分的公开审计。要哪些文件见[贡献指南](../.github/CONTRIBUTING.md#changing-the-rubric)，`validate.py` 会查它们在不在。几条通过的提案可以合成一个版本。
3. **征求意见。** pull request 里写明意见征求到哪天截止：小版本从开出起至少 30 天，大版本至少 60 天。每一条反对意见都在 pull request 里回复，我们不同意的，回复也留在记录里。
4. **独立复核。** 发布前，我们请至少一位和见润科技没有商业关系的人（高校的研究者或独立从业者）读草案和标定记录。征得本人同意后，他们的意见随版本一起公开。找不到人的，发布说明里照实写。
5. **发布和公告。** 新文件合入，上一版标为已取代；已发布的量表文件从不原地修改。实现新版本的那个工具版本，在中英两份更新日志和 GitHub 发布说明里写明：改了什么、为什么、证据是什么、榜单怎么动了。[量表 README](README.md) 的版本表加一行。

工具的 bug 不是量表改动。工具读错了一个站，修复按[稳定性说明](../guide/stability.md#what-a-minor-or-patch-release-may-do)作为补丁版本发布，更新日志写明是哪一项、往哪个方向变。补丁版本从不改权重、档位或档位线。

## 分数什么时候会变

公开的分数只有这四种情况会变：

- **量表出了新版本。** 旧分数不重算、不改标：`AIV 62（v1.1）`永远是 v1.1 的分。不同版本的分数不放在一起比、不求平均；要比，就用当前版本重新打分。
- **工具修了错。** 修正错误结果的补丁版本会让个别站的分数变，规矩见上。
- **网站自己变了。** 这正是分数要量的东西。
- **榜单重跑。** 每一轮只用一个工具版本、在一个地方跑，并写明是哪个版本、哪一天。哪一行看着不对，走[榜单更正](../.github/ISSUE_TEMPLATE/benchmark_correction.yml)表单，对着 `benchmark/raw/` 里存的那份报告核。

分数从不因为有人付了钱、因为一个站是不是客户、因为一条没有证据的投诉而变。

## 同一个版本，谁跑都是同一个分

目标是：任何人用同一个版本给同一个站打分，得到同一个分。靠这几条撑着：

- 已发布的量表文件从不修改。JSON 是给机器读的标准文本，check id 永久不变：可以退役，不会挪给别的检查用。
- 每份报告都写明量表版本、工具版本、日期和抽到的 8 个网址，别人能照原样再跑一遍。
- 每个工具版本都一直能装、能锁定版本（`uvx geo-score@X.Y.Z`），新版本出了，旧版本照样能跑。
- 工具对着量表做测试：check id、分值、档位、档位线、门槛封顶都必须和 JSON 一致；测试用的样例站把每一项该落在哪一档都钉死了。每次合并前都要跑 `scripts/check.sh`。
- 谁都可以自己实现这套量表。改了权重的实现，不要把它的数叫 AIV 分。两个实现在同一个真实页面上打分不一致，我们当作规范本身有漏洞，记下来。

仍然会有差异的地方：网站两次返回的页面或内容不一样；某个请求失败了，它支撑的那一项记为不可观测，不记 0 分；有四项靠启发式判断。这些会让分数动多少，是公开测的，换新工具版本会重测（[REPRODUCIBILITY.md](../benchmark/REPRODUCIBILITY.md)）。单个站的分数按 ±5 来读，不当成精确值。

## 和标准组织的关系

我们把这套量表当开放规范来经营：免费读、免费实现、免费引用、欢迎批评，MIT 协议，修改历史全部保留。我们打算一直保持这个形式。

- 我们不花钱买任何标准的发起单位或主办单位席位。正常的会费，或照实列明、按工作量分摊的起草成本，不算席位；真有这类支出，我们会公开写明。
- 只有在依法登记的社会团体按它公开的程序来邀请、标准文本任何人都能免费读、量表继续开放并和标准保持一致时，我们才参与起草。
- 参与之前，我们请律师看这类标准适用的规定原文（国内的团体标准，看《团体标准管理规定》）和这个团体的章程。
- 以这套量表为基础的标准，应该只给准备度打分。引用、提及、名次这些结果，应该和这里一样单独报告；要把它们并进分数，我们不支持。
- 我们不把这套量表说成国家标准、行业标准或认证，也不把自己说成标准制定单位。

## 这一页怎么改

走 pull request，并记进两份更新日志。凡是放宽上面关于利益冲突或标准组织的规矩，和量表小版本一样，公开征求意见至少 30 天。
